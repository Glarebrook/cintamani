# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Cintamani is a browser-based Snake game served as static files from a NAS web server (e.g. Synology Web Station, NGINX). There is no build step, no bundler, and no package manager — `index.html` is the entry point and is served as-is. The game logic is authored as native ES modules (`<script type="module">`), which requires zero tooling in any modern browser.

The pre-rewrite V1 implementation (global `<script>` tags, no modules) is no longer in the working tree — it was kept in a `V1/` folder for reference/rollback for a while, then deleted once it stopped being useful. It's still recoverable from git history (it was committed) if ever needed; there's nothing on disk to avoid editing anymore.

## Collaboration model

The user is a game designer/planner with no software engineering background — not a developer. Treat every feature request or question from them as **a direction/idea, not a spec to implement literally**. A word-for-word implementation of what they say can conflict with the existing architecture in ways they can't be expected to foresee. Development authority — how something actually gets built — rests with you (acting as both dev PM and engineer), not with the literal wording of their request.

For any nontrivial request (new feature, behavior change, "what do you think about X"), follow this loop before writing code:
1. **Design, as a dev PM**: figure out how the requested element fits into the current architecture (see below) — which module(s) it touches.
2. **Assess module fit**: decide whether it fits into existing modules/registries as-is, needs a new module (e.g. a new `content/enemies/*` or `content/mechanics/*` entry), or requires rearranging existing ones.
3. **Explain in plain language**: describe, in non-technical terms, what the current behavior is and what you propose to change — assume no coding knowledge.
4. **Get approval before implementing.**

This mirrors how `EnterPlanMode`/`ExitPlanMode` already work in this environment — for this project, treat that plan → approve → execute flow as the default for feature work, not just for large rewrites.

## Branching and version workflow

Adopted 2026-07-27. `master` is the stable/release branch — always in a shippable state. `dev` is a single, long-lived, reused branch where all new feature work happens (not one branch per feature) — the user explicitly chose this simpler model over per-feature branches, understanding the tradeoff: everything currently on `dev` moves to `master` together at merge time, so if an in-progress feature isn't ready (or isn't safely inert) when a different, finished feature needs to ship, finish or neutralize the in-progress one first rather than trying to cherry-pick just the finished piece off a single shared branch.

Workflow: implement + headless-verify (see Commands below) + user browser-tests on `dev` → once confirmed, merge `dev` into `master` → add a new row to README.md's 변경 이력 (changelog) table → tag the merge commit (`git tag vX.Y.Z`) so that exact shipped state can always be revisited or rolled back to. Baseline: `v2.1.0` tag = the state right before this workflow was introduced.

**Bump `BUILD_VERSION` (`config/constants.js`) and the `?v=` cache-busting string in `index.html` together, on every change during `dev` iteration too** — not just at the master merge point. `BUILD_VERSION` is rendered on-screen (bottom-right of the canvas, `render/layers.js`'s `versionLayer`) specifically so the user can tell, just by glancing at the running game, whether a page refresh actually picked up the latest code — this was added after a real instance of the user being unsure whether a visual change had landed. Keep both strings equal and bump both whenever either JS or CSS changes.

NAS deployment mechanism (git-pull vs. manual file copy) was not yet confirmed with the user as of this writing — don't assume merging to `master` alone puts changes live; ask before claiming a change "went live." Since the leaderboard feature (see Architecture below) landed, deployment is no longer "just static files" — the NAS copy must also include the `api/` folder (PHP 8.2, confirmed available via Synology Web Station) with a *writable* `api/data/` directory, or score submission will fail even though the game itself loads fine.

## Commands

There is no build/lint/test tooling in this repo (no `package.json`). Development loop is:

- **Run locally**: serve the folder root with any static file server and open `index.html`, e.g. `python3 -m http.server` from the project root.
- **Cache busting**: every `<script>`/`<link>` tag in `index.html` carries a `?v=YYYYMMDD-N` query string. Bump this string whenever JS/CSS changes, so the NAS-served static files aren't served stale from browser cache.
- **No automated test framework.** For quick headless logic checks during development, `jsc -m` (JavaScriptCore's CLI, ships with macOS at `/System/Library/Frameworks/JavaScriptCore.framework/Versions/A/Helpers/jsc`) can execute ES modules directly and is useful for smoke-testing pure logic (e.g. `js/algorithms/floodFill.js`, `js/content/mechanics/*`) without a browser — stub `window`/`document`/`performance`/`requestAnimationFrame` on `globalThis` first if importing anything that touches the DOM; also stub `fetch` (e.g. a queue-based stub whose responses you resolve on demand) if importing anything that touches `js/services/leaderboardApi.js` or `states/gameOverState.js`, and give the `document` stub real `classList`/`addEventListener`/`focus`/`appendChild`/`createElement` behavior (not just a bare `{ textContent: '' }`) since `render/leaderboardPanel.js` calls all of these. This is not a committed test suite, just a technique — test scripts live outside the repo in a scratch directory, not checked in. Ultimately, verify gameplay changes by running the game in a browser, and PHP endpoints (`api/*.php`) by hitting them on the actual NAS — nothing in this repo can execute PHP.

## Architecture

**Native ES modules, no bundler.** `index.html` loads a single `<script type="module" src="js/main.js">`; every dependency is resolved via `import`/`export`, not script-tag order. When adding a new file, wire it in via an explicit `import` somewhere in the graph — there is no auto-discovery.

**Two coordinate spaces.** Game/collision logic operates entirely in *grid cell* coordinates (integers within `GRID_W × GRID_H`, from `config/constants.js`). Only `render/*` and `core/gridMath.js` (`toPixel`/`toCell`) convert to pixels. Work in cell space; convert only at the point of drawing.

**`World` object**: `game.js` builds one `world` object (`{ snake, enemyManager, itemManager, projectileManager, eventBus, stats, startTime, reset() }`) and passes it by reference into states/systems/managers. Restarting the game does **not** create a new `world` object — it calls `world.reset(options)`, which reassigns `world`'s fields in place (new `Snake`, new `EnemyManager`, etc.). This matters: states and systems must always read through `world.snake` / `world.enemyManager` etc. at call time, never destructure and cache those references at construction time, or a restart won't be picked up. `reset`'s only option is `{ testMode }` (default `false`) — the title screen's `t` key starts with `TEST_MODE_INITIAL_LENGTH`/`TEST_MODE_TICK_MS` instead of the normal `SNAKE_INITIAL_LENGTH`/`TICK_MS` defaults, for quickly exercising longer-snake/faster-tick behavior (e.g. `sentinel`/`turret`'s length-20 spawn gate) without having to play up to it first; `entities/snake.js`'s `Snake` constructor takes the initial length as a parameter (`initialLength = SNAKE_INITIAL_LENGTH`) specifically so `reset` can pass either constant through. `world.stats` (`{ tickMs, attackDamage, scaleWaveDamage, enemyKillStacks }`) holds the *current-run* values of things that used to be read directly off the `TICK_MS`/`PROJECTILE_DAMAGE`/`SCALE_WAVE_DAMAGE` constants — those constants are now only the reset-to defaults; anything that needs the live value (the game loop's tick interval, `fire()`'s projectile damage, `fireScaleWave()`'s area damage, the HUD) must read `world.stats.*`, since items like `speedUp`/`speedDown`/`attackUp` mutate it mid-run. `attackUp` (the orange food) bumps both `attackDamage` (`ATTACK_UP_DELTA`, +1) and `scaleWaveDamage` (`ATTACK_UP_SCALE_WAVE_DELTA`, +3) on a single pickup — two separate constants, not one shared delta, since venom and scale wave don't scale at the same rate. `core/loop.js` takes a `getTickMs()` callback rather than a fixed `tickMs` for exactly this reason — the interval can change after the loop has already started. `enemyKillStacks` is a plain `{ [enemyTypeId]: count }` map, reset fresh on every `world.reset()`, that any enemy type's `onDefeated` hook can accumulate into (see `basic.js`) — generic across type ids on purpose, since which enemy owns a given kill-stack reward has already been reassigned once (it started on `chaser.js`, moved to `basic.js`) and will likely move again.

**Fixed-tick game loop, split from per-frame updates** (`core/loop.js`): `createGameLoop` drives a `requestAnimationFrame` loop that calls `onFrame(dt)` every frame (continuous things: projectile motion, food spawn timer) and `onTick()` at most once per frame once accumulated time crosses `TICK_MS` (discrete grid movement: `snake.step`, collision, enemy spawn timer). This is a single `if`, not a catch-up `while` loop — matches the original timing model exactly; don't "fix" it into a catch-up loop without checking that's actually wanted.

**A large frame-to-frame gap is clamped, not honored** (`MAX_FRAME_GAP_MS = 250` in `core/loop.js`): if the tab is backgrounded or the OS sleeps, the next `requestAnimationFrame` callback can fire with a `timestamp` that's seconds (even minutes) ahead of the previous one. Left unclamped, that gap does two bad things — `onFrame(dt)` gets handed an enormous `dt`, and worse, the tick check (`timestamp - lastTick >= tickMs`) stays true for many frames after resuming, and because the tick branch is a single `if` (per above), each of those frames fires exactly one more "catch-up" tick — meaning the snake ticks once per *rendered* frame (e.g. every ~16ms) instead of once per `tickMs` (e.g. 120ms) for as long as it takes the backlog to drain, which reads as the snake teleporting into a wall or itself. This was a real, reported bug: sitting idle on the game-over screen (where `onTick()` is a no-op, so the backlog silently keeps building while backgrounded) and then restarting *before* the backlog had fully drained let the leftover catch-up burst carry into the freshly-started `playing` state, killing it almost immediately. The fix clamps both the `dt` passed to `onFrame` and `lastTick` itself to at most `MAX_FRAME_GAP_MS` behind the current frame whenever the raw gap exceeds that — the backlog is discarded, not processed, which is the opposite of a catch-up loop (don't confuse the two if you touch this).

**Game state machine** (`core/stateMachine.js` + `states/*.js`): currently `title`, `playing`, `gameOver`, and `leaderboardView`; `title` is the initial state, not `playing`. Each state is `{ enter(payload), exit(), onFrame(dt), onTick(), render() }`. `game.js`'s loop always delegates to `stateMachine.current`. States bind their own key actions on `enter()` and unbind on `exit()` via the shared `input/actions.js` singleton (e.g. `playingState` binds Space→fire). `gameOverState` is the one state whose `enter(payload)` is `async` and does *not* bind Enter→`goToTitle` immediately — see the leaderboard paragraph below for why. `titleState` binds two specific keys — `Enter` and `t` — each calling `onStart({ testMode })` with a different flag; `onStart` (really `game.js`'s `startGame`) is what actually calls `world.reset(options)` and transitions to `playing`. (An earlier version used a generic `Actions.bindAny(onStart)` "press any key" fallback; that was removed once the title screen needed to distinguish *which* key was pressed, and nothing else in the codebase used `bindAny`, so it was deleted from `input/actions.js` rather than left unused.) This is why restart-on-Enter only works while `gameOver` is active, without an explicit `if (gameOver)` check anywhere, and why the flow is always title → playing → gameOver → title, never gameOver → playing directly. `input/actions.js`'s `normalizeKey` lowercases single-character keys before matching, so `bind('t', ...)` fires regardless of Shift/Caps Lock — worth knowing before adding another letter-key binding.

**Movement direction input is a short queue, not a single slot** (`input/input.js`): `Input.consume()` is called once per game tick (`playingState.js`'s `onTick()`), and a tick can be as short as `MIN_TICK_MS` (40ms) at max speed. The original version kept only one `pending` direction, overwritten by the next `keydown` — a real, reported bug: two arrow-key presses within one tick window (very reachable at 40–120ms, especially for fast/practiced players) meant only the *second* press survived, silently dropping the first ("입력이 씹힘"). Fixed by buffering up to `MAX_QUEUE` (2) queued directions in a FIFO; `consume()` shifts one off per call instead of always returning the same `applied` value, so two quick taps now land as two separate turns over the next two ticks instead of collapsing into one. The reversal check (`isReverse`, blocks 180° self-reversal) had a second, subtler bug baked into the single-slot version: it compared the new keypress only against `applied` (the *last-tick* direction), not against whatever was still sitting unapplied in `pending` — so a fast up-then-down double-tap while moving right could have its second press validated against the stale "right" instead of the about-to-apply "up," letting an illegal reversal slip through. The queue version fixes this by checking each new key against `queue[queue.length - 1]` (the most recently *reserved*, not yet applied, direction) when the queue is non-empty, falling back to `applied` only when the queue is empty — i.e. always validate against what the snake's direction will actually be by the time this new input would take effect.

**`Input` is a page-lifetime singleton, so it needs an explicit `reset()` — `world.reset()` doesn't touch it.** Every other piece of run state lives on `world` and gets reassigned fresh by `world.reset()` (see the `World` object paragraph above), but `input/input.js`'s `queue`/`applied` are module-level variables that persist across restarts by construction — nothing about starting a new game ever re-imports the module. This was a second real, reported bug, closely related to the queue one above: a direction key pressed absent-mindedly on the game-over screen (or right before dying) stayed queued/applied, and then fired at the very start of the *next* run with the player having pressed nothing new — best case an unexpected early turn, worst case (if the stale direction was directly into the snake's own starting body layout) instant self-collision on tick one, which reads as "the game rushes into a wall/itself the moment it starts." `playingState.js`'s `enter()` now calls `Input.reset()` (clears the queue, resets `applied` back to the default rightward direction) alongside its existing `pendingDirection = null` — note that `pendingDirection = null` alone was never sufficient, since `onTick()` unconditionally overwrites it with whatever `Input.consume()` returns on the very first tick regardless.

**Pause is an in-state flag on `playingState`, deliberately not a state-machine state.** `P` and `Escape` both call a `togglePause()` closed over a local `paused` boolean (bound/unbound in `enter()`/`exit()` alongside the existing `Space`→`fire` binding). Adding a real `'paused'` state was considered and rejected: transitioning *out* of `playing` would run `playingState.exit()`/re-`enter()` on resume, and `enter()` deliberately resets several pieces of delicate mid-run state (`Input.reset()`, `pendingDirection = null`, `passThroughGrace = false` — see the `Input` singleton and pass-through-forgiveness paragraphs) that a genuine pause must *not* touch — losing `passThroughGrace` mid-pause, for instance, could let a real self-collision through incorrectly right after resuming from inside a just-closed loop. Keeping it as a flag means `onFrame`/`onTick` simply return immediately when `paused` (freezing every timer, movement, and collision check untouched, including things like `passThroughGrace`), while `render()` still runs normally every frame and then layers `render/overlays.js`'s `renderPauseOverlay(ctx)` (dark overlay + "PAUSE" text, same visual language as `renderGameOverOverlay`) plus `statusPanel.renderDimOverlay()` on top — so the frozen game and status panel stay visible but dimmed, not blanked. `fire()` itself also checks `paused` and no-ops, since `Space` stays bound throughout a pause (unbinding/rebinding it would be extra bookkeeping the flag check avoids).
- **Paused wall-clock time is excluded from survival time and score, via a single `world.startTime` adjustment — not by patching every consumer.** `survivalMs` (used by `die()`'s event payload and, downstream, `getScoreBreakdown`'s `survival` component) and the HUD's live `survivalSeconds` are both computed as `performance.now() - world.startTime` at their respective call sites; rather than threading pause-awareness into each of those, `togglePause()` records `pauseStartedAt` when pausing and, on resume, does `world.startTime += performance.now() - pauseStartedAt` — shifting the reference point forward by exactly the paused duration, so every existing `- world.startTime` computation automatically excludes it without modification. The one spot that still needed a direct fix: `render()`'s live `survivalSeconds` uses `performance.now()` as "now," which would otherwise keep counting up *during* the pause itself (before the resume-time adjustment ever happens) — fixed by substituting `pauseStartedAt` as the "now" reference whenever `paused` is true, so the displayed number holds steady for the whole pause instead of jumping only at resume.

**Two ranged weapons, both gated behind in-run milestones, both sharing the Space key.** `world.stats.venomUnlocked` (독침/venom needle — the flavor name for the plain projectile) flips true the first time `snake.segments.length >= VENOM_UNLOCK_LENGTH` (8) is observed in `onTick`, after growth resolves; `world.stats.scaleWaveUnlocked` (비늘파동/scale wave, a charge-and-release area attack) flips true once `venomUnlocked` is *already* true **and** `killsByType[chaserEnemy.id] >= SCALE_WAVE_UNLOCK_CHASER_KILLS` (5) — the ordering dependency is deliberate, not incidental: scale wave's whole interaction model ("release before full charge falls back to venom") presupposes venom already works, so the check requires `venomUnlocked` as a precondition rather than letting the two unlock independently. Both checks live in an `if / else if` chain (not two independent `if`s) specifically so at most one tutorial popup triggers per tick — if both conditions somehow became true the same tick, the second waits one tick (120ms, imperceptible) rather than stacking two popups at once. Both flags, once set, stay `true` for the rest of the run regardless of later length/kill-count changes (e.g. shrinking below 8 via `speedDown` does not re-lock venom) — same "permanent within a run" shape as `maxLength`/`maxSpeedLevel`'s score bonuses.
- **Unlocking either weapon for the first time pauses the game and shows a small popup, dismissed only by Enter.** `showTutorial({ iconKey, iconColor, title, lines })` sets `activeTutorial`, pauses (reusing the exact same `paused`/`pauseStartedAt` machinery as manual P/Esc pause, including the `world.startTime` catch-up adjustment on dismiss — see the pause paragraphs above), and calls `Actions.bind('Enter', dismissTutorial)`. This used to be dismiss-on-any-key (`Actions.bindAny`, a modal override that briefly resurrected `bindAny`/`unbindAny` in `input/actions.js` after they'd been deleted once already — see the Game state machine paragraph above), but that let an absent-minded arrow-key press during the popup silently dismiss it before the player had actually read it (a real reported issue — "방향키 눌러서 넘어가져서 뜨는지도 모르고 휙 넘어가게 됨"). `bindAny`/`unbindAny` were deleted a second time when this switched to `Actions.bind('Enter', ...)`; `dismissTutorial` calls `Actions.unbind('Enter')`, and `exit()` does the same defensively in case a tutorial is still up when the state is torn down. `render/overlays.js`'s `renderTutorialPopup(ctx, { icon, iconColor, title, lines })` now draws three tiers instead of one flat list: a small icon at the top (`icon` — looked up live via `getWeaponIcon(iconKey)` every frame, same "re-check load state each render" convention as the enemy/cintamani icons, so a still-loading image at the moment the popup opens picks up automatically once it finishes; falls back to a filled circle in `iconColor` — venom's `'#f5d742'`, scale wave's `'#ffffff'`, matching each weapon's own established color — if no icon file is loaded yet), a bold larger-font `title` line ("이무기가 독침발사를 배웠다!" / "이무기가 비늘파동을 배웠다!"), and the pre-existing smaller-font `lines` (the actual "how to use it" instructions) below that. `assets/weapons/venom.png`/`scaleWave.png` follow the same hand-drawn-template convention as `assets/enemies/`/`assets/cintamani/` (`assets/weapons/README.md`), loaded through `render/statusIcons.js`'s `getWeaponIcon(key)` — which, along with `getEnemyIcon`/`getCintamaniIcon`, now shares one `createIconLoader(keys, pathFor)` factory (extracted once a third near-identical load-plus-fallback-plus-trim icon set showed up, same "past that point duplication stopped being the pragmatic choice" reasoning as `grantKillReward`) and the same transparent-padding-trimming `drawIcon` described above. **Test-mode runs skip the tutorial (but not the unlock itself).** `TEST_MODE_INITIAL_LENGTH` (40) already exceeds `VENOM_UNLOCK_LENGTH` (8), so a test-mode run would otherwise hit the venom tutorial — and the resulting pause — on literally its first tick, defeating test mode's whole "quickly exercise gated content" purpose (same rationale that already made test-mode skip the leaderboard). Both `if (!world.testMode) showTutorial(...)` guards leave `venomUnlocked`/`scaleWaveUnlocked` being set exactly as before; only the popup/pause is skipped, so weapons are immediately usable in test mode without interruption. **Test mode also pre-seeds `killsByType[chaserEnemy.id] = SCALE_WAVE_UNLOCK_CHASER_KILLS`** in `game.js`'s `world.reset()` — length alone already gets venom "for free" in test mode (40 ≥ 8), but scale wave's other precondition (5 chaser kills) has no equivalent free ride from the starting stats, so without this seed a tester would have to go kill five chasers by hand before ever reaching the scale-wave code path. With it, `scaleWaveUnlocked` flips true one tick after `venomUnlocked` does (the `else if` chain resolves them on consecutive ticks — see above), so both weapons are live within ~240ms of a test-mode run starting. This is purely a testing convenience and has no effect on normal (non-test) runs, where `killsByType` still starts empty and 5 real chaser kills are still required.
- **Space is handled by raw `keydown`/`keyup` listeners owned by `playingState.js`, not `Actions.bind`, once venom is in play.** This is a deliberate exception to the rest of the codebase's `Actions`-based key handling: `Actions` only supports keydown-fires-once semantics, but the scale-wave charge mechanic needs to know *how long* Space was held, which requires a `keyup` — a capability `Actions` doesn't have and wasn't extended to have, to avoid widening that shared module's contract for a need only one key currently has. `onSpaceDown`/`onSpaceUp` are added/removed directly on `window` in `enter()`/`exit()` (mirroring the lifecycle discipline `Actions.bind`/`unbind` already enforces, just one level lower). The behavior branches on unlock state: not `venomUnlocked` → Space does nothing; `venomUnlocked` but not `scaleWaveUnlocked` → keydown fires venom immediately (old single-shot behavior, unchanged); `scaleWaveUnlocked` → keydown starts a charge timer (`chargeStartAt`, guarded against OS key-repeat re-triggering it via a `!== null` check) and keyup reads the held duration — `>= SCALE_WAVE_CHARGE_MS` (1000ms) fires the scale wave, anything shorter falls back to a normal venom shot. This fallback (not "fire nothing" on an early release) was a deliberate design choice: it means releasing Space always does *something*, so a quick tap keeps behaving like the player's muscle memory expects even after the charge mechanic is unlocked.
- **`render/overlays.js`'s `renderChargeGauge(ctx, headX, headY, ratio, full)`** draws a small bar just above the head — `playingState.js`'s `render()` computes `ratio` from `chargeStartAt` fresh every frame (not stored), so the gauge fill is always exactly in sync with real elapsed hold time; `full` (ratio ≥ 1) swaps the fill color, the player's visual cue that releasing now fires the wave instead of venom.
- **`fireScaleWave()` computes its hit area as the union of a "+"-shaped cross around *every* snake body segment**, not a single blob around the head — `SCALE_WAVE_RANGE` (3) cells up/down/left/right from each segment, deduplicated through a `Set` keyed by `"x,y"` before being turned back into a plain array (both for the hit-test and for `world.scaleWaveEffect.cells`, which `render/layers.js`'s `scaleWaveLayer` paints white for `SCALE_WAVE_FLASH_MS` and then stops drawing on its own — nothing needs to clear it). An enemy counts as hit if *any* cell of its full `ENEMY_SCALE × ENEMY_SCALE` drawn footprint intersects the affected set (same "hit box matches what's drawn" principle as `checkHeadCollision`/`checkEnemyHeadCollision` elsewhere), not just its center cell. Damage goes through `enemyManager.applyProjectileHit(enemy, world.stats.scaleWaveDamage)` — meaning `canBeDamagedByProjectile: false` enemies (sentinel/turret, capture-only) are immune to the wave for the same reason they're immune to venom, not a separate rule. (`world.stats.scaleWaveDamage` starts at the `SCALE_WAVE_DAMAGE` constant and is raised by `attackUp` pickups — see the `World` object paragraph above.) A kill from the wave calls the enemy's `onDefeated` hook (not `onCaptured`) and is scored as `SCORE_PER_KILL_PROJECTILE` — categorized with venom as "killed by damage," distinct from capture, since that's the more accurate lineage even though the wave itself is neither literally a projectile nor an encirclement.
- **`grantKillReward(enemy, scoreAmount)`** is a small helper extracted inside `playingState.js` bundling the four things that always travel together on a kill (particle burst, `killScore` `+=`, score popup, `killsByType` `+=`) — used by both the encirclement-capture loop and `fireScaleWave()`'s kill loop. This is the third near-identical copy of that bundle to appear in the codebase (the first two are this capture loop's prior inline form and `managers/projectileManager.js`'s own separate copy for venom kills) — past that point duplication stopped being the pragmatic choice, hence the extraction; `projectileManager.js`'s copy was deliberately left as its own module's business rather than importing across the module boundary for one shared helper.
- **The projectile-centering fix**: `render/layers.js`'s `projectileLayer` was drawing its circle centered at `px + size/2` (`size` being the projectile's own, smaller-than-a-cell diameter) instead of `px + CELL_SIZE/2` (the cell's actual center) — since `size < CELL_SIZE`, this visibly offset every venom shot toward the cell's top-left corner, including at the exact moment it spawns from the snake's head (`fire()` itself was always spawning at the correct grid coordinate — `head.x, head.y` — the bug was purely in how that coordinate got converted to a pixel position for drawing, not in the spawn logic).

**Event bus** (`core/eventBus.js`): used *only* for decoupled reactions, not for same-tick, order-critical decisions. Concretely: `playingState` emits `'playerDied'` when a real (non-forgiven) collision ends the run; `game.js` is the sole subscriber, transitioning the state machine to `gameOver`. Collision resolution itself (wall → mechanics → self-collision → enemy → food, see below) stays direct synchronous function calls in `systems/collision.js` / `states/playingState.js`, precisely because that ordering must not be reorderable by listener registration.

**`content/` is the extensibility surface — enemies, items, and capture-style mechanics are all registry-based.** Each category (`content/enemies/`, `content/items/`, `content/mechanics/`) follows the same pattern: plain def files export a config object with no dependency on the registry, and that category's `index.js` imports each def file and calls `registry.register(def.id, def)`. **Do not** have a def file import its own category's registry and self-register — `basic.js`/`sentinel.js` (etc.) must stay one-directional imports (constants in, def object out) to avoid a circular-import/TDZ failure between the def file and `index.js`. Adding a new enemy type, item, or mechanic is: one new def file + one import+register line in that category's `index.js` — never a change to `managers/*`, `systems/collision.js`, or `render/*`.

- **Enemy types** (`content/enemies/`): config fields are `color, hp, canBeDamagedByProjectile, displayText(enemy), collidesWithHead`, plus a growing set of optional hooks (below). `managers/enemyManager.js` never special-cases a type id; enemy instances carry a `typeDef` reference resolved once at spawn time, not a raw type id. `checkHeadCollision` treats the enemy's full `ENEMY_SCALE × ENEMY_SCALE` drawn footprint as the hit box, not just its center cell — matching `render()`'s box is deliberate, since a hit box smaller than what's drawn reads as "sometimes doesn't work" to a player.

  - `spawnEligible(world)` gates whether the type can currently spawn. It receives the real `world` object (not just the snake), because eligibility isn't always snake-length-based: `sentinel.js` and `turret.js` share a length gate (`LONG_SNAKE_UNLOCK_LENGTH`, named for the condition rather than either enemy so reassigning it elsewhere doesn't need a rename — see the reward-constant naming note above), while `hunter.js` gates on `world.stats.tickMs` instead (only spawns once the snake is faster than `HUNTER_UNLOCK_TICK_MS`). `_trySpawn(world)` also enforces a hard `ENEMY_MAX_COUNT` cap on simultaneous enemies *before* even filtering by `spawnEligible` — an early return, not a filter, since there's no point scanning the grid for candidate cells if the field's already full. `_trySpawn` picks the *type* before it picks a *cell*, not the other way around (an earlier version picked them independently) — a `captureZone` type needs its whole capture-zone square on-grid, so the candidate-cell scan has to already know which type it's placing before it can know how much edge margin to reserve. The margin is computed inline from `ENEMY_SCALE * typeDef.captureZone.scale`, the same formula `getCaptureZoneBounds` uses, so it isn't a separate field to keep in sync. This isn't just cosmetic: a `captureZone` enemy spawned exactly on the border row/column (`x === 0`, etc.) is **permanently uncapturable**, not just hard to reach — `algorithms/floodFill.js` seeds every border cell as "reachable from outside" unconditionally, so that enemy's own cell can never register as enclosed no matter how the snake moves. The candidate-cell scan also excludes any cell within `ENEMY_MIN_SPAWN_DISTANCE_FROM_HEAD` (Chebyshev distance, same square-region convention as the capture-zone margin and `chaser.js`'s aggro square) of `world.snake.head` — added after a reported instance of an enemy spawning right next to the head and ending the run before the player had any chance to react; this check applies to every type, not just `collidesWithHead` ones, since it's cheap and there's no upside to ever spawning that close.
  - `captureZone: { scale }` opts the type into the encirclement mechanic (below).
  - `move(enemy, world)` + `moveIntervalMs(enemy, world)` opt the type into self-movement — `move` returns a `{x,y}` cardinal step, `moveIntervalMs` the current ms interval between steps. Both `chaser.js` (id 3) and `hunter.js` (id 5) move at a fixed, hardcoded interval (`CHASER_BASE_MOVE_MS`, `HUNTER_MOVE_MS`) that deliberately does **not** track `world.stats.tickMs` — the snake speeding up or slowing down via `speedUp`/`speedDown` pickups should not change how fast these enemies move; that decoupling was an explicit correction after `hunter.js` initially *did* mirror the snake's live speed. `chaser.js` still needs the full `world` (not just the snake) in `moveIntervalMs`, though: it switches to a 2× faster interval once the snake enters its detection square, and that distance check reads `world.snake`. `managers/enemyManager.js`'s `updateMovement(dt, world)` calls both hooks generically for any type that defines them, accumulating a per-enemy `moveTimer`; static types (`basic`/`sentinel`/`turret`) simply don't define `move` and are skipped. It's called from `onFrame(dt)` with real per-frame `dt`, deliberately separate from `update(dt, world)` (the spawn timer, called from `onTick` with the snake's tick-sized `dt`) — a moving enemy's interval can be shorter than the snake's own tick interval, and updating movement only once per snake tick would silently cap every enemy at "at most one step per tick," hiding any speed difference. `chaser.js`'s non-aggro wander is a biased random walk, not a memoryless one: `enemy._wanderDir` is committed to for `CHASER_WANDER_STEP_MIN`–`CHASER_WANDER_STEP_MAX` moves (a "streak," re-rolled once it runs out) rather than re-randomized every single move, specifically so the enemy visibly drifts in one direction for a while before turning, instead of jittering in place — a direct response to the old behavior (uniform-random every step) looking too erratic. `CHASER_WANDER_JITTER_CHANCE` layers a per-step chance of returning a fully random direction *without* touching the committed streak's direction or remaining-count — jitter only ever perturbs that one move's return value, so streak length stays governed purely by the MIN/MAX reroll schedule regardless of how many jitters land inside it. (One consequence worth knowing if you touch this: since jitter picks uniformly from all 4 `DIRS` including the committed one, only 3/4 of jitter rolls are *visibly* different from what a non-jittered move would've returned — the effective "looks different" rate is `CHASER_WANDER_JITTER_CHANCE * 3/4`, not the raw constant. The headless test for this (`test_chaser_wander.mjs`) checks against that adjusted rate.)
  - `onDefeated(world, enemy)` fires once, only when this specific enemy is killed via a projectile (see `managers/projectileManager.js`) — not for capture-based removal, a different path. `basic.js` (id 1) uses it to accumulate a per-type-id kill counter in `world.stats.enemyKillStacks` and spawn a purple-food bonus every `PURPLE_FOOD_KILL_STACK_THRESHOLD` kills; `chaser.js` (id 3) uses it for something un-stacked instead — every single kill spawns a yellow food immediately at that exact death cell via `itemManager.spawnAt('speedUp', enemy.x, enemy.y)`.
  - `onCaptured(world, enemy)` is the capture-removal counterpart to `onDefeated` — fires once per enemy removed by the encirclement mechanic; `states/playingState.js`'s `onTick()` calls it right after `enemyManager.removeByIds()`, which returns the removed enemy objects for exactly this purpose. `sentinel.js` (id 2) uses it for a flat-chance orange-food drop (`ORANGE_FOOD_DROP_CHANCE`, at a random free cell via `spawnSpecific`); `turret.js` (id 4) uses it for a three-way weighted drop table at the death cell (`spawnAt`) — mostly plain food, sometimes a yellow+orange pair placed in adjacent cells, rarely a brown. Which reward lives on which enemy id has already been reshuffled once this session (id 1 and id 3 swapped what they used to do, id 2 and id 4 similarly). Because of that churn, the reward constants in `config/constants.js` are named after the *reward* (`PURPLE_FOOD_KILL_STACK_THRESHOLD`, `ORANGE_FOOD_DROP_CHANCE`), not after whichever enemy currently triggers it — reassigning a reward to a different enemy id shouldn't require renaming the constant.
  - `ability(enemy, world, dt)` + `abilityCooldownMs(enemy, world)` opt the type into a generic timed side effect, same shape as `move`/`moveIntervalMs` but for anything other than repositioning. `managers/enemyManager.js`'s `updateAbilities(dt, world)` calls both generically, also from `onFrame`. The cooldown only gates the *firing*, not the condition check: once the timer clears the cooldown, `updateAbilities` calls `ability()` every single frame until it returns truthy, and only resets the timer on that truthy return — a version that instead sampled the condition once, exactly at the moment the cooldown elapsed, would go silent for seconds at a time whenever that one sampled instant happened not to be aligned (this was an actual shipped bug in `turret.js`, fixed the same way). `ability()` must therefore return whether it actually fired. `turret.js` (id 4, continuous threat) uses the cooldown as-is: fire on a fixed cadence for as long as the snake stays aligned on its row/column. `hunter.js` (id 5, burst-on-entry) needs a different rhythm — one 3-shot burst spread over ~1s exactly when the snake *enters* alignment, silent again until it leaves and re-enters — so it sets `abilityCooldownMs: () => 0` (the outer gate is effectively off) and manages its own edge-detection (`enemy._wasAligned`) and burst schedule (`enemy._burstShotsLeft`/`_burstTimer`) using the `dt` it's passed directly, entirely inside its own `ability()`. Both are valid uses of the same two-hook shape; which one fits is a per-type design choice, not something the hook itself enforces.
- **Items** (`content/items/`): config fields are `color` and `onPickup(world, item)`, plus optional `spawnEligible(world)` (same gating pattern as enemies) and optional `overlayText` (small white text drawn centered over the item's cell, e.g. `tripleGrowth.js`'s `'x3'` — same idea as an enemy's `displayText`). As of this writing `food.js` (green) is the *only* def without `spawnEligible: () => false` — `speedUp`, `speedDown`, `tripleGrowth`, and `attackUp` are all reward-only, each hardcoding `spawnEligible` to `false` so the ambient random timer can never produce them; every one is instead spawned deterministically or probabilistically from a specific enemy's `onDefeated`/`onCaptured` (see above). Don't assume this 4-reward/1-ambient split is permanent — it's shifted before and the mechanism (the `spawnEligible: () => false` convention) is what's stable, not which items currently use it.

  `managers/itemManager.js` manages a `foods` array and three distinct ways to add to it, each with different rules:
  - `spawnItem(snake, enemyManager)` is the ambient path — called from `update(dt, ...)` on a timer re-rolled to a random `FOOD_SPAWN_MIN_MS`–`FOOD_SPAWN_MAX_MS` delay after every spawn (same "re-roll after firing" shape as `enemyManager._randomSpawnDelay`), and respects the `FOOD_MAX_COUNT` cap. It picks uniformly at random among all `spawnEligible`-passing registered types via a shared `_findFreeCell` helper — never hardcodes an item id, even though in practice only `food` currently passes the filter.
  - `spawnSpecific(typeId, snake, enemyManager)` places one instance of a given type at a random free cell, skipping the eligibility filter *and* the `FOOD_MAX_COUNT` cap. Used for reward drops that should land somewhere on the map but aren't tied to a specific cell (`basic.js`'s kill-stack bonus, `sentinel.js`'s capture-chance drop).
  - `spawnAt(typeId, x, y)` places one instance at an exact given cell, also uncapped. Used for reward drops that should appear at the spot where something just died (`chaser.js`'s per-kill drop, `turret.js`'s capture-table drops).

  The cap distinction is deliberate, not an oversight: `FOOD_MAX_COUNT` (currently 5) is scoped to the passive ambient spawner only — a combat reward is a one-off deterministic-or-rolled response to a player action and would feel broken if it silently failed to appear because the field happened to already be cluttered with ambient food. `checkHeadCollision` matches by grid position and splices out just the one eaten. Stat-changing items (`speedUp`/`speedDown`/`attackUp`) mutate `world.stats` (see below) rather than a constant, so effects persist for the rest of the run.
- **Mechanics** (`content/mechanics/`): each is `{ id, suppressesSelfCollision, tick(world, outlineCells) }`. `systems/collision.js`'s `runMechanicsTick` calls every registered mechanic once per game tick and collects `{capturedIds}`-shaped results; `checkSelfCollision` forgives a self-collision if any `suppressesSelfCollision` mechanic captured something that same tick. `content/mechanics/encirclement.js` is the current (and so far only) one: `algorithms/floodFill.js` (a game-agnostic BFS flood fill from the grid border) computes which cells are reachable from outside the snake's body, and `findEnclosingRing` (a second BFS from the enemy's cell through non-snake/non-reachable cells) determines whether that enemy's cell is currently topologically sealed off, and if so, which snake cells form the seal. Capture only fires on the **edge** where an enemy transitions from not-enclosed to enclosed (tracked per enemy object in a module-level `WeakMap`, not per tick's raw state) — checking raw "is it currently enclosed" every tick would let a spot that got sealed off by coincidence much earlier (while the player was elsewhere, not even trying to wrap that enemy) capture the moment the head later wanders back through the zone for any unrelated reason. On the tick of that transition, capture additionally requires: the snake head is within that enemy's gray capture-zone square (`getCaptureZoneBounds`, side = enemy outline cells × `captureZone.scale`) at that exact moment, and the specific sealing ring lies entirely within that same square (body segments elsewhere, outside the zone and not part of the ring, don't disqualify it). `WeakMap` keyed by the enemy object (not its numeric id) is deliberate — it means a restart (new `EnemyManager`, brand-new enemy objects) never needs an explicit reset call; old entries just become unreachable. A future "trap"-style mechanic follows the same shape and registers alongside it — `collision.js` doesn't change.

**Collision order is a hand-written, non-negotiable sequence** (`states/playingState.js.onTick()`, backed by `systems/collision.js`): wall → run all mechanics → self-collision (forgiveness, see below) → enemy head-on collision (always fatal, regardless of capture-zone state) → food pickup → growth → enemy spawn-timer update. If you touch collision handling, preserve this order — splitting mechanics and the self-collision check apart (e.g. running mechanics after checking self-collision) breaks capture-then-pass-through.

**Projectiles carry an `owner` (`entities/projectile.js`, default `'player'`) and `managers/projectileManager.js.update(dt, world)` branches its whole collision policy on it** — a player projectile ignores the snake and damages enemies; an `owner: 'enemy'` one ignores enemies entirely and instead always ends the game on head contact, or calls the projectile's own `onBodyHit(world)` callback on body contact. That callback (plus an analogous `onHeadHit(world)`, called before the game-over signal fires) is supplied by whichever enemy spawned the projectile, not hardcoded in `projectileManager.js` — `turret.js` passes `onBodyHit: w => w.snake.shrink(TURRET_PROJECTILE_SHRINK)`, `hunter.js` passes one that both shrinks and slows the snake by exactly the `speedDown` item's amounts. This is what lets two different `owner: 'enemy'` sources (turret, hunter) share one collision codepath in the manager without the manager needing to know which type fired. The head-contact check is the one lethal check that deliberately sits *outside* the `onTick()` sequence above: `update()` returns `{ headHit }`, and `playingState.js`'s `onFrame()` calls `die()` immediately if it's `true`, rather than waiting for the next tick. That's intentional, not an oversight — projectiles move continuously (every frame, like the food-spawn timer), so a hit can happen between ticks, and holding it until the next `onTick()` would let the snake visually pass through a lethal hit for up to one tick's worth of frames first.

**`checkEnemyHeadCollision` is checked from both `onTick()` and `onFrame()` — not a duplicate, two complementary cases.** The `onTick()` call (in the collision sequence above) catches the head moving onto an enemy via `snake.step()`. But a *moving* enemy (`chaser.js`, `hunter.js`) updates its own position from `onFrame`'s `updateMovement`, on its own clock — and that clock can run faster than the snake's tick (e.g. `chaser` aggro'd is 60ms against a 120ms tick). If the only check were in `onTick()`, an enemy could step onto the head's cell and step off again entirely between two tick-boundary samples — a real bug that shipped once, reported as "the hitbox feels smaller than what's drawn." The fix mirrors the projectile-headHit pattern exactly: `onFrame()`, right after `updateMovement`, re-runs `checkEnemyHeadCollision(world)` and calls `die()` immediately if it's now true, without waiting for the next tick.

**Pass-through forgiveness spans multiple ticks, not just the exact capture tick** (`passThroughGrace` in `states/playingState.js`): a loop around a captureZone enemy very often closes via an ordinary move into an empty cell (no self-collision that tick — the enemy is just removed cleanly), and the *actual* body-crossing only happens a tick or more later, once the snake is trapped inside the loop it just drew and has to move through its own body to get out — by which point the enemy is already gone, so a same-tick-only forgiveness check would find nothing to forgive and wrongly kill the player. `passThroughGrace` is set to `true` whenever a mechanic captures something (whether or not that move collided), stays `true` across every subsequent tick that *is* a self-collision (so the snake can keep pushing through a tightly-wound loop for as many ticks as it takes), and only clears on a tick where the head lands on a free cell (proof the snake is actually clear). A genuinely unrelated self-collision (no recent capture, grace already clear) still ends the game normally.

**Growth is a queue, not a single slot** (`entities/snake.js`, `growQueue`): eating schedules a pending growth position; `checkGrowth()` resolves each pending entry independently once the snake's body has fully vacated that cell. This must stay a queue (not a single `growPos` value) — food respawns immediately after being eaten, so eating a second food before the first one's growth has resolved is routine, and a single-slot design silently drops the earlier growth. Shrinking (`snake.shrink(n)`, used by the `speedDown` item) is immediate, not queued — it removes from the tail right away and always leaves at least 1 segment.

**Rendering is an ordered layer list** (`render/layers.js`): background → capture-zone squares → items → snake (tail-to-head so the head ends up on top) → projectiles → enemies → particles → build-version text. `render/renderer.js` just iterates it; `render/hud.js` handles the DOM stats bar (separate from canvas drawing); `render/overlays.js` draws state-specific overlays (currently just game-over; a future Paused/Menu overlay belongs here too).

**Status panel is a third, wholly separate canvas** (`#status-canvas` in `index.html`, sized in `main.js` to `GRID_W*CELL_SIZE` wide × `STATUS_PANEL_HEIGHT` (100) tall, drawn by `render/statusPanel.js`'s `createStatusPanel()`) — not a layer on the game canvas, and not a DOM element like `hud.js`. It sits below the game canvas and shows four columns: snake stats (speed/length/독침 [venom-needle, the flavor name for the projectile] damage), enemy-kill-by-type tally, a 2×2 grid of "여의주" (cintamani — the code uses this English/Sanskrit name for the wish-fulfilling-jewel concept, not a phonetic romanization of the Korean, specifically to keep it visually distinct from "yeouiju" and aligned with the game's own title) counts, and an empty fourth column reserved for a future concept. Follows the exact same "create once in `game.js`, call `.render(world)` from every state's own `render()`" pattern as `hud`/`leaderboardPanel` — both `playingState.js` and `gameOverState.js` call `statusPanel.render(world)` (so it freezes on the last frame during game-over, same as everything else), and `game.js` calls it once immediately after `createWorld()` so it isn't blank on the title screen before any run has started.
- **`world.stats.killsByType`** (`{ [enemyTypeId]: count }`) is a *new*, separate counter from the pre-existing `enemyKillStacks` — don't conflate them. `enemyKillStacks` is reward-trigger plumbing that only some `onDefeated` hooks opt into (e.g. `basic.js`'s purple-food-every-5-kills). `killsByType` is unconditionally incremented at *both* kill sites (`managers/projectileManager.js`'s player-kill branch, `playingState.js`'s `onTick()` capture loop) for every enemy type, purely so the status panel has something generic to display — it has no gameplay effect. It resets every `world.reset()` (this-run-only, not a cross-session lifetime counter — confirmed with the user; a persistent version would need `localStorage`, which nothing in this codebase uses yet).
- **`world.stats.cintamani`** (`{ red, blue, green, yellow }`, all wired to always be `0`) exists purely so column 3 has real data to bind to rather than hardcoded zeros in the render code — the mechanic itself doesn't exist yet. When it's designed, the increments plug into `world.stats.cintamani.*` and the panel needs no changes.
- **Icons are optional, direction-agnostic images with a color-shape fallback** — same graceful-degradation pattern as the (since-reverted) snake sprite attempt: `render/statusIcons.js` loads `assets/enemies/enemy{1..5}.png` and `assets/cintamani/{red,blue,green,yellow}.png` once at module load (guarded behind `typeof Image !== 'undefined'` for headless-test safety, exactly like `snakeSprites.js`), and `getEnemyIcon(id)`/`getCintamaniIcon(key)` return `null` until that specific file both exists and has loaded. `statusPanel.js`'s `drawIconOrFallback` draws the image if present, otherwise a filled circle in the enemy's own `typeDef.color` (or the cintamani's own fixed color) — so the panel looks intentional immediately, before any art is supplied. `assets/enemies/README.md` and `assets/cintamani/README.md` are the drawing templates (exact filenames, square PNG, transparent background, 64×64 recommended) — the user draws these by hand; this was an explicit choice over auto-generated placeholder art, unlike the icon style question this was asked about directly.
- **`getEnemyIcon(id)` isn't status-panel-exclusive — `managers/enemyManager.js`'s own `render()` (the actual on-field enemy drawing, unrelated to the status panel) imports it too**, so the same `assets/enemies/enemy{id}.png` file simultaneously reskins both the kill-stack icon *and* the enemy's real in-field appearance the moment it's added — there's no separate "field sprite" asset to draw. Same fallback rule both places: no file yet → the existing flat `typeDef.color`-filled square (field) or circle (status panel). Field rendering keeps drawing the HP number (`displayText`) on top of whatever's underneath, image or not — that's gameplay-relevant text, not decoration, so it isn't gated behind art being supplied.
- **`statusIcons.js`'s `drawIcon(ctx, img, dx, dy, dw, dh)` auto-crops transparent padding out of hand-drawn icon art before drawing it, rather than stretching the raw file to fill the target box.** This exists because a real reported issue: hand-drawn 64×64 PNGs don't necessarily use every pixel edge-to-edge, and `ctx.drawImage(icon, x, y, size, size)` with the raw image visibly reads as smaller than the color-square/circle fallback it replaces, even though both are drawn into the exact same bounding box — the gap is empty margin baked into the artwork, not a sizing bug in the draw call itself. On each image's `load` event, `computeTrim(img)` draws it once into an offscreen canvas, scans `getImageData` for the bounding box of non-fully-transparent pixels, and stores that rect in a `WeakMap` keyed by the `Image` element (not attached to the image object itself, so `getEnemyIcon`/`getCintamaniIcon`'s return type is unchanged). `drawIcon` looks up that rect and, if present, uses the 9-argument form of `ctx.drawImage` to source only the trimmed region — so the actual drawn character always fills the full target box regardless of how much dead space surrounds it in the source file. An image with no transparent margin (or one that's fully transparent, or one whose pixels can't be read, e.g. opened via `file://`) has no entry in the map and falls back to drawing the untrimmed image, unchanged from before. Both `managers/enemyManager.js` and `render/statusPanel.js` call `drawIcon` instead of `ctx.drawImage` directly, so the fix applies to field enemies and the status-panel icons identically.
- The leather-look background (`BG_COLOR` '#d9b98a' base + thin translucent dark-brown diagonal hatching, column dividers in solid dark brown) is drawn fresh every `render()` call — nothing about it is cached or precomputed, it's cheap enough (a handful of `fillRect`/line draws at 800×100) not to matter.
- **The two canvases visually merge into one screen on `title`/`leaderboardView`, and split apart again on `playing`/`gameOver`.** `index.html` wraps `#canvas-stage` (holding `#game-canvas`) and `#status-canvas` in a `#play-area` container; `css/style.css`'s default `#play-area` has an 8px gap and each canvas keeps its own full border (visually two separate boxes), while `#play-area.merged` drops the gap to 0 and removes the touching borders (`#game-canvas`'s `border-bottom`, `#status-canvas`'s `border-top`) so the pair reads as one continuous framed box. `statusPanel.setMerged(bool)` toggles that class (`add`/`remove`, not `classList.toggle` — deliberately, so a test's DOM stub only needs `add`/`remove` implemented, not the less-commonly-stubbed `toggle`); each state calls it once in its own `enter()` — `titleState`/`leaderboardViewState` call `setMerged(true)`, `playingState`/`gameOverState` call `setMerged(false)` (the latter is technically redundant given the fixed `title → playing → gameOver → title` flow, since `playing`'s `enter()` already set it `false` on the way in, but it's set explicitly anyway so `gameOverState` doesn't depend on an invariant owned by a different file — same philosophy as `playingState.js`'s explicit `Input.reset()`). While merged, `statusPanel.renderBlank()` (called every frame from `titleState`/`leaderboardViewState`'s `render()`, alongside `renderTitleScreen`/`renderLeaderboardViewBackground`) fills `#status-canvas` with the *exact* same solid color those two functions use for the main canvas (`TITLE_BG_COLOR` '#111111', kept in sync by hand between `statusPanel.js` and `render/overlays.js` — a shared constant was judged overkill for one color value that only needs to match in one spot) — without this, the merged box would show a black title screen glued to a leftover tan/leather panel underneath, which defeats the point of removing the seam.

**Hit feedback (particles + head flash)**: two lightweight, purely-visual reactions, added because kills/pickups felt inert without them — neither affects gameplay state, both are safe to skip reading if you're only tracing gameplay logic.
- `entities/particle.js` + `managers/particleManager.js` mirror `entities/projectile.js`/`projectileManager.js`'s shape (plain object, `{x,y,vx,vy}`, updated every frame) but add a `life`/`maxLife` (ms) instead of collision detection — `particleManager.update(dt)` (called from `playingState.js`'s `onFrame`, no `world` arg needed since particles don't interact with anything) just moves them and drops any with `life <= 0`. `spawnBurst({x,y,color,count,speed,life})` fires `count` particles in an evenly-spaced circle (`angle = 2π·i/count`) — this is the only way particles get created. Rendering (`particleLayer` in `render/layers.js`) is on the manager's `particles` getter, same split as projectiles (manager holds state, `layers.js` draws it); alpha is faded by `life/maxLife` so the burst visibly dies out rather than popping off abruptly. `world.particleManager` is created once per `world.reset()` in `game.js`, same as every other manager.
- Two call sites trigger a burst, both using the *defeated enemy's own color* (`enemy.typeDef.color`) at its position: `managers/projectileManager.js`, right after `hitEnemy.typeDef.onDefeated?.(world, hitEnemy)` fires (player-projectile kill), and `states/playingState.js`'s `onTick()`, inside the loop over encirclement-captured enemies, right after `enemy.typeDef.onCaptured?.(world, enemy)`. Both are direct synchronous calls (`world.particleManager.spawnBurst(...)`), not routed through `eventBus` — the effect is fired from exactly the same spot the game-logic hook already runs, so there's no decoupling need `eventBus` would justify, and every test/dev world object that reaches either code path must now also provide a `particleManager` (a few hand-built test worlds needed a `createParticleManager()` added when this landed).
- **Item-pickup flash is a head→tail traveling wave, not just a head blink** — it's `Snake` instance state (`flashColor`, `flashElapsedMs`, alongside `growQueue`'s precedent for "transient gameplay-adjacent state living on the Snake instance"), unrelated to particles. `snake.startFlash(color)` is called from `playingState.js`'s food-pickup point in `onTick()`, using the eaten item's own color (`ItemTypes.get(eaten.type).color`) — no separate lookup table, whatever the item's registered `color` is is what flows down the body. Rather than a single on/off timer, each segment `i` has its own flash window that starts at `i * ITEM_FLASH_STAGGER_MS` and lasts `ITEM_FLASH_DURATION_MS` (`Snake.isFlashingAt(index)` computes this from the shared `flashElapsedMs` clock — no per-segment state, just arithmetic against one running elapsed counter) — so the head lights up immediately and each segment further back lights up progressively later, reading as a pulse flowing tail-ward, not a simultaneous full-body blink. `snake.updateFlash(dt)` is called every frame from `onFrame` (not `onTick`) so the wave's speed is wall-clock-accurate regardless of the snake's current tick speed; it clears `flashColor` back to `null` once `flashElapsedMs` passes the point where even the *current* tail segment's window has closed (recomputed against `segments.length` every call, so growth mid-wave naturally extends the wave rather than needing special-casing). `render/layers.js`'s `snakeLayer` calls `isFlashingAt(i)` per segment while drawing (tail-to-head, same order as before) and swaps in `flashColor` only for whichever segments are currently in their window — a hard on/off per segment, not a fade, since a brief solid-color blink sweeping down the body was the intended feel ("반짝이며 흘러가는").

**Real-time score** (`core/score.js`, `config/constants.js`'s `SCORE_PER_*`): added because the leaderboard originally ranked by raw `survivalMs` alone, which rewards the *opposite* of engaged play — since growing the snake only adds self-collision risk with zero score benefit, the optimal strategy under pure survival-time ranking is to never eat and just dodge forever. The fix is a `world.stats.baseScore` that accumulates from every actual accomplishment as it happens, plus length- and speed-based bonuses recomputed live:
- Rather than one lump `baseScore`, `world.stats` tracks three purely-additive components separately — `survivalScore`, `killScore`, `itemScore` — each `+=`'d at the moment its thing happens: `SCORE_PER_SECOND * (dt/1000)` every frame in `playingState.js`'s `onFrame` into `survivalScore` (this is what makes the on-screen number visibly creep upward continuously rather than jump once per tick), `SCORE_PER_ITEM` into `itemScore` at the food-pickup point in `onTick`, and into `killScore` at *both* kill sites — `managers/projectileManager.js`'s player-projectile-kill branch (`SCORE_PER_KILL_PROJECTILE`) and `playingState.js`'s `onTick()` encirclement-capture loop (`SCORE_PER_KILL_CAPTURE`, deliberately worth 4× more — see the balance note below) — the same two spots that already trigger a particle burst (see Hit feedback below), so a kill's score/particle/reward-hook/popup effects all fire together in one place per kill type. The three-way split (rather than one `baseScore`) exists so the leaderboard name-entry screen can show *where* the score came from, not just the total — see the Leaderboard section's score-breakdown bullet.
- **Score weights were tuned against a headless simulation, not guessed.** A scratch script (not committed — lives outside the repo per the Commands section's testing convention) ran ~200 simulated runs with a simple "avoid danger, path toward the nearest food, shoot when aligned" bot built on the real `Snake`/`EnemyManager`/`ItemManager`/`systems/collision.js` modules, and tallied what fraction of the final score came from each component. Two things this bot — deliberately not given any encirclement-capture logic, since faking that well enough to be trustworthy was judged harder than it was worth — never or almost never obtained: a capture-based kill (0 in 200 runs) and any meaningful speed-level gain (avg. 0.1% of total score), because both require picking up a reward-drop item that basic play rarely produces, and captures specifically require deliberate loop-building that a "just survive" heuristic doesn't stumble into. Since those are the two hardest things a human can pull off in this game, and the pre-tuning weights valued them at essentially the same rate as trivially easy actions (a capture earned the same flat amount as shooting a stationary enemy; a speed level earned a rounding error next to survival time), `SCORE_PER_KILL_CAPTURE` was split out from `SCORE_PER_KILL_PROJECTILE` and set to 4× it (200 vs. 50), and `SCORE_PER_SPEED_LEVEL` was raised 5× (20 → 100). Re-running the same simulation afterward shows near-identical aggregate percentages — expected and not a sign the change did nothing: this particular bot still can't *reach* those actions, so their weight change doesn't show up in its numbers. The point of raising them was for the human players who *can* reach them, not to move this bot's baseline.
- `world.stats.maxLength` tracks the highest `segments.length` reached this run (updated in `onTick` right after `checkGrowth()`), independent from the snake's *current* length — this matters because `shrink()` (the `speedDown` item) removes segments immediately, and a length-based score bonus must not let the player lose points they already earned by momentarily eating a shrink item. `world.stats.maxSpeedLevel` follows the exact same "peak reached, never decays" shape for speed: updated in the same spot in `onTick`, from `core/speedLevel.js`'s `getSpeedLevel(world.stats.tickMs)` (see the speed-display paragraph below) — reaching a faster speed and later eating a `speedDown` item doesn't claw back the speed bonus already earned.
- `core/score.js`'s `getTotalScore(world)` is the single source of truth for the displayed/final number: `baseScore + (maxLength - initialLength) * SCORE_PER_LENGTH_SEGMENT + (maxSpeedLevel - initialSpeedLevel) * SCORE_PER_SPEED_LEVEL`. Both bonus terms are *recomputed from scratch* on every call (neither is itself a `+=` accumulator) specifically so they can never be double-counted or drift out of sync with `maxLength`/`maxSpeedLevel` — call it as many times as you want per frame, same answer. `world.stats.initialLength`/`initialSpeedLevel` exist because test-mode runs start at `TEST_MODE_INITIAL_LENGTH`/`TEST_MODE_TICK_MS` rather than the normal defaults; each bonus baseline must match whichever starting value a given run actually had, or test-mode runs would show a huge phantom bonus for length/speed they started with, not length/speed they earned.
- Display is DOM, not canvas, and lives **outside the canvas entirely** — `#stat-score` in `#stats-bar` (`index.html`), the same bar that already held the other live stats, restructured with `justify-content: space-between` into `#stats-left` (attack/length/speed/survival, in that order) and the score docked at the far right — i.e. visually top-right of the whole play area, not just top-right of the canvas. `render/hud.js`'s `update()` takes a `score` field now (both `playingState.js` and `gameOverState.js` pass `getTotalScore(world)` on every `render()` call, so it keeps updating live during play and then freezes at whatever it last was once the run ends, same freeze behavior the other stats already had). There is no separate canvas score layer — an earlier version drew it directly on the canvas top-right corner, but that put it *inside* the gameplay screen, which is specifically what this was moved away from.
- **Score popups** (`entities/scorePopup.js`, `managers/scorePopupManager.js`, `render/layers.js`'s `scorePopupLayer`) are the separate, canvas-rendered "+20"-style feedback that appears at the exact spot an item was eaten or an enemy was killed — unrelated to the DOM total above, and deliberately still on the canvas since it's tied to a world position, not a persistent readout. Structurally this is `entities/particle.js`/`managers/particleManager.js`'s shape copied one level up (position + `life`/`maxLife`, `update(dt)` drops expired ones) but simpler — one popup per spawn instead of a burst, drifting straight up at a constant `SCORE_POPUP_RISE_SPEED` instead of radiating outward, and rendering as `fillText` instead of a filled circle. `scorePopupManager.spawn(x, y, amount)` is called from the same three score-`+=` sites above (`playingState.js`'s item-pickup and capture-kill points, `projectileManager.js`'s projectile-kill point) — every place `baseScore` goes up by a fixed amount also spawns the matching popup showing that amount, so the two can never drift out of sync (there's no separate "which amount do I show" lookup). `world.scorePopupManager` is created once per `world.reset()` in `game.js`, same as every other manager — any hand-built test world that reaches one of those three call sites needs one too (same requirement `particleManager` already imposed).
- **The leaderboard now ranks by this computed score, not raw survival time** — this was a deliberately staged rollout: the score system shipped display-only first (so the weights could be played with and tuned — see the simulation-based balance note above — before they became permanent), and only once that tuning pass was done did submission/ranking switch over. See the Leaderboard section below for the migration details (in particular, how pre-existing entries that predate this system are handled).

**Speed display has a cosmetic offset separate from the underlying speed unlock and score math** (`core/speedLevel.js`, `config/constants.js`'s `SPEED_LEVEL_DISPLAY_OFFSET`). `getSpeedLevel(tickMs)` is the one raw calculation (`Math.round((MAX_TICK_MS - tickMs) / FOOD_SPEED_DELTA_MS)`, unchanged math, just extracted out of `hud.js` into its own module so `core/score.js`'s speed bonus and `render/hud.js`'s display share the exact same numbers) — this raw value is what feeds `world.stats.initialSpeedLevel`/`maxSpeedLevel` and therefore the score bonus. `render/hud.js`'s `toDisplaySpeedLevel(tickMs)` is `getSpeedLevel(tickMs) + SPEED_LEVEL_DISPLAY_OFFSET` (4) — purely a "what number does the player see" cosmetic shift so a fresh run reads "20" instead of "16", requested because the raw starting number felt arbitrary to the user. The offset is intentionally excluded from `core/score.js`'s math: since the score bonus is always a *difference* (`maxSpeedLevel - initialSpeedLevel`), adding a constant to both sides would cancel out anyway, so keeping it purely in the display path (rather than, say, baking it into `getSpeedLevel` itself) is both correct and the smaller change. The old "N단계" (rendered as "16 단계") wording was also dropped at the same time — `index.html`'s speed stat now shows a bare number, matching how every other stat (attack/length/survival) is already just a number with a label in front, not a label-plus-suffix.

**Leaderboard** (`api/leaderboard.php`, `js/services/leaderboardApi.js`, `js/render/leaderboardPanel.js`, wired into `states/gameOverState.js`): the first server-side code, first network I/O, and first real HTML `<input>` UI in this codebase — everything before this was static files + canvas + read-only DOM stat spans.

- Backend is a single PHP file (`api/leaderboard.php`, avoids needing any `.htaccess`/rewrite config) handling `GET` (return top scores) and `POST` (`{name, survivalMs}` → validate, append, re-sort desc, trim to `LEADERBOARD_MAX_ENTRIES`, persist) against `api/data/leaderboard.json` (`flock()`-guarded reads/writes, no DB). No serious anti-cheat — a casual home-NAS leaderboard, not a competitive product — only sanity validation (name trimmed/length-capped, `survivalMs` must be a finite positive number under a generous cap). `api/data/*.json` is gitignored (runtime user data, not source).
- `js/services/leaderboardApi.js` wraps `fetch()` and **never throws** — network/API failures return `{ ok: false, error }` instead of rejecting, because the game-over screen must keep working even before `api/leaderboard.php` is deployed or if the NAS is briefly unreachable.
- `js/render/leaderboardPanel.js` is a DOM controller in the same spirit as `hud.js` ("DOM is separate from the canvas renderer") but is the first one built around a real `<input>` (`#leaderboard-name-input` in `index.html`, inside `#leaderboard-overlay` absolutely-positioned over `#game-canvas` via `#canvas-stage` in `css/style.css`) — a real `<input>` is required for Korean IME name entry to work at all; there is no canvas-based text-entry pattern anywhere in this codebase and none should be built for this. Each entry also carries a `ts` (unix seconds, stamped server-side by `api/leaderboard.php` at write time) which the panel formats to local-timezone `YYYY-MM-DD HH:mm:ss` for display — formatting is a client concern since the server has no timezone notion, it just calls `time()`. `LEADERBOARD_NAME_MAX_LENGTH` (200) is generous on purpose; the panel wraps long names (`overflow-wrap: anywhere` on `.leaderboard-name`) and stacks name+time above the date on its own line rather than truncating, so a long name degrades gracefully instead of breaking the layout.
- **The name-entry screen shows the final score, broken down by where it came from, not just raw survival time.** `playingState.js`'s `die()` snapshots `getScoreBreakdown(world)` (see Real-time score above) into the `'playerDied'` event payload alongside `survivalMs` — a snapshot, not a live read, for the same reason `survivalMs` already was one: `gameOverState.js` shouldn't have to re-derive it later from a `world` that (in principle) could already be mid-reset by the time some async step resumes. `gameOverState.js` forwards `scoreBreakdown` straight through to `panel.showEntryPhase(entries, survivalMs, scoreBreakdown)`. `leaderboardPanel.js` renders it inside `#leaderboard-my-score` as a receipt, not a sentence — a first version joined the components with "+" into one line (`생존 X점 + 적 처치 X점 + ...`), but that read poorly, so it's now three pieces: a `#my-score-total` line (total score, big and gold), a `#my-score-breakdown` bullet list (one `<li>` per component — survival/item/kill/bonus, each its own line prefixed `· `), and a `#my-score-bonus-detail` bullet list unpacking the bonus line specifically (length/speed, prefixed `– ` and CSS-indented, so it visually reads as a sub-list of the "가산점" bullet above it rather than a fourth independent component). `renderBulletList(ul, lines)` (a small shared helper) clears and rebuilds each `<ul>` via `createElement`/`textContent` per line, same no-`innerHTML` convention as `renderList()`'s leaderboard rows. `leaderboardViewState.js` doesn't pass a `scoreBreakdown` (it only calls `showResultPhase`, which hides the whole form including this block, so there's nothing to fill in anyway).
- **Ranking migrated from `survivalMs` to `score`.** `submitScore(name, survivalMs, score)` (`services/leaderboardApi.js`) now sends both — `survivalMs` is still stored for reference but the server no longer sorts by it. `api/leaderboard.php` validates `score` (finite, `0 ≤ score ≤ MAX_SCORE`) the same way it already validated `survivalMs`, and `usort`s entries by `score` descending instead. **Pre-existing entries have no `score` field** (they predate this system), and rather than a one-off migration script run against the live NAS data (which isn't reachable from this repo — `api/data/*.json` is gitignored, real user data), `read_entries()` backfills it lazily on every read: `score = round(survivalMs/1000 * LEGACY_SCORE_PER_SECOND)`, i.e. treats an old entry as "survival score only, zero bonus" — consistent with how `core/score.js`'s formula already degrades when there's no length/speed data, so it's not a special case so much as the same rule applied with missing inputs defaulting to zero. This backfilled value isn't just computed for display — because `write_entries()` always re-serializes the *entire* array, the very next `POST` after deployment persists the backfilled `score` back into the JSON file for every legacy entry, so the lazy computation only actually runs until the first write. `LEGACY_SCORE_PER_SECOND` is a PHP-side constant that must be kept in sync with `config/constants.js`'s `SCORE_PER_SECOND` by hand (no shared source between the JS and PHP runtimes) — it exists solely for this backfill and shouldn't be used for anything else. `leaderboardPanel.js`'s per-row display (`renderList`'s `.leaderboard-record` span) switched from `formatSeconds(entry.survivalMs)` to a new `formatScore(entry.score)` to match — survival time is no longer shown in the compact per-row list at all (still present in the stored data if ever needed again), only in the detailed breakdown on the entry-phase screen for the player's own just-finished run. The "which row is mine" match in `gameOverState.js` (`result.entries.findIndex(...)`) switched from comparing `survivalMs` to comparing `score`, for the same reason the sort key changed.
- **`game.js` creates exactly one `leaderboardPanel` (`createLeaderboardPanel()`, no constructor args) and shares it between `gameOverState` and `states/leaderboardViewState.js`** — same "create once" pattern as `hud`. Since the underlying DOM elements are singletons, creating the panel twice would double-register the form's `submit`/skip-button `click` listeners. Because submit/skip handling is specific to whichever run just ended, the panel exposes `setHandlers({ onSubmit, onSkip })` instead of taking them at construction — `gameOverState` calls it once, `leaderboardViewState` never calls it at all (it only ever calls `panel.showResultPhase()`, which hides the form entirely, so there's nothing for a leftover handler to trigger even though the panel object is shared).
- **`states/leaderboardViewState.js`** is a read-only leaderboard screen reachable from the title screen (`titleState` binds `'l'` alongside `'Enter'`/`'t'`) — for looking at standings without starting a run. It reuses `panel.showResultPhase(entries, -1)` verbatim (same visual as gameOverState's post-submit screen: form hidden, list shown, "ENTER - 타이틀로" footer) rather than introducing a third panel mode, and binds `Enter` to go back to `title` the same way `gameOverState`'s result phase does.
- `gameOverState.enter(payload)` is `async`: it kicks off `fetchLeaderboard()` and shows the panel's **entry phase** (name input focused) immediately. It deliberately does **not** call `Actions.bind('Enter', onRestart)` yet — `input/actions.js`'s global listener sits on `window` keydown with `preventDefault()`, which would otherwise steal the Enter keystroke a player types into the name `<input>` to submit the form. Instead, the panel's own `<form submit>` handler owns Enter while the input has focus (native browser behavior: Enter in a focused `<input>` inside a `<form>` fires that form's `submit` event, which nothing intercepts since Actions isn't bound to `'Enter'` yet). Only after the user submits or hits skip does the state move to the **result phase** (`finish()`) and *then* bind `Actions.bind('Enter', onRestart)`, restoring "Enter → title." `exit()` unbinds Enter and hides the panel.
- **Test-mode runs (title screen's `t`) never reach the leaderboard at all.** `world.reset({testMode})` now also sets `world.testMode` (read live off `world`, same convention as `world.stats` etc. — never cached at construction time). If `world.testMode` is true, `gameOverState.enter()` returns immediately after binding `Actions.bind('Enter', onRestart)` — no `fetchLeaderboard()` call, no panel shown — restoring the pre-leaderboard "Enter instantly returns to title" behavior for that path specifically. This exists because test-mode runs start with an artificially inflated length/speed (`TEST_MODE_INITIAL_LENGTH`/`TEST_MODE_TICK_MS`) purely to exercise length/speed-gated content quickly; letting those scores land on the shared leaderboard next to genuine runs would make the rankings meaningless.
- Two guards exist against a real race that surfaced during headless testing: the leaderboard `GET`/`POST` responses are async, but the player can act (click skip, or a fast submit) before they resolve. A `generation` counter (bumped on every `enter()`/`exit()`) discards a response that arrives after the state has been left and re-entered; a `phase` flag (`'entry'` → `'result'`, set the instant the player submits/skips) discards a response that arrives after the player already moved past the entry phase — without the `phase` guard, a slow `GET` arriving after skip would silently revert the result screen back to the name-entry form. Both guards are checked identically after every `await` in `gameOverState.js`; if you add another async step here, guard it the same way. `leaderboardViewState.js` carries the same `generation` guard for its own single `fetchLeaderboard()` call, for the same reason.
